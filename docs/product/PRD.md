# 产品定位

本平台不是传统“学院部门官网”，也不是单纯的信息发布站。

它的定位是：

> **人工智能学院学生参与竞赛、寻找伙伴、加入组织、报名活动与获取科创指导的一站式校园服务入口。**

平台希望解决的不是“有没有通知”，而是学生在真实参与过程中遇到的连续问题：

```text
我不知道最近有什么值得参加
        ↓
我找到一个竞赛 / 活动 / 组织
        ↓
我不知道自己是否适合
        ↓
我不知道什么时候截止
        ↓
我缺队友 / 不知道怎么加入
        ↓
我需要指南 / 咨询
        ↓
我真正完成报名、申请或参与
```

产品核心不是“展示”，而是：

```text
发现机会
获取可信信息
找到合适的人
完成报名 / 申请
获得指导
```

---

# 产品目标

V0.1 的目标是把学院常见但分散的信息和流程收拢到一个稳定、可维护的网站中。

平台第一阶段重点解决：

- 竞赛信息分散
- 截止日期难追踪
- 学生不知道适合参加什么
- 团队赛找不到队友
- 社团 / 组织招新信息分散
- 活动报名依赖临时二维码或表格
- 常见问题重复咨询
- 部门成员发布和维护信息缺少统一后台

V0.1 不追求：

- 全学院数字化管理
- 即时聊天
- 复杂社交网络
- AI Agent
- 竞赛自动抓取
- 复杂推荐算法
- 成果统计系统
- 复杂组织内部权限
- 多级审批
- 积分 / 排行榜 / 社交热度

# 核心产品原则

## 信息必须可信

竞赛、活动、招新、指南等内容应由学院平台运营人员或对应组织负责人维护。

官方链接、截止时间、组织主体、更新时间应明确展示。

平台不以“算法推荐”替代事实信息。

---

## 用户优先看到行动信息

比起宣传文案，学生更需要看到：

```text
正在报名
什么时候截止
是否团队赛
是否适合大一
哪里报名
哪里找队友
是否正在招新
活动还有没有名额
```

因此页面优先展示：

```text
状态
日期
要求
入口
下一步操作
```

---

## 浏览尽量不强制登录

游客可浏览大部分公开信息。

只有发生个人行为时要求登录，例如：

```text
报名活动
发布组队
申请加入队伍
申请组织招新
关注竞赛
提交咨询
查看个人申请状态
```

---

## 平台首先是服务工具

不做无业务价值的：

- 点赞
- 粉丝
- 热度排名
- 虚假 KPI
- 游戏化等级
- “科创达人 Lv.8”
- 无意义积分

---

## 组织成员

组织成员是一种附加身份：

```text
OrganizationMembership.role = MEMBER
```

V0.1 中：

> **组织成员基本不获得额外管理权限。**

主要用途：

- 个人资料展示所属组织
- 为后续组织功能预留关系模型

例如：

```text
人工智能协会 · 技术部成员
```

其平台能力与普通学生基本一致。

---

## 组织负责人

定义：

```text
OrganizationMembership.role = LEADER
```

权限作用范围仅限对应组织。

例如：

```text
张三
AI协会 -> LEADER
机器人协会 -> 无身份
```

张三可以管理 AI 协会相关内容，但不能管理机器人协会。

V0.1 可以：

- 编辑自己负责组织的公开资料
- 发布招新
- 编辑招新
- 结束招新
- 查看自己组织的招新申请
- 接受 / 拒绝申请

负责人从“社团组织 -> 我的组织 -> 进入管理”进入指定组织的工作台，不在学生端一级导航或个人中心中放置全局组织管理入口。

V0.1 不可以：

- 创建其他组织
- 给其他人授予负责人
- 修改平台角色
- 管理全平台竞赛
- 管理全平台活动
- 管理其他组织
- 创建复杂内部部门

---

## 平台运营人员

平台角色：

```text
OPERATOR
```

主要负责公共平台内容。

可以：

- 发布 / 编辑竞赛
- 管理竞赛时间线
- 发布 / 编辑学院活动
- 查看活动报名名单
- 发布通知
- 管理 FAQ / 指南
- 回复咨询
- 管理明显违规公开内容

不默认拥有：

- 全局用户权限管理
- 超级管理员能力
- 所有组织负责人权限

---

## 超级管理员

平台系统级角色。

人数应很少。

负责：

- 用户管理
- 创建 / 配置组织
- 分配组织负责人
- 分配 / 撤销平台运营权限
- 禁用异常账号
- 系统级数据维护
- Django Admin 高权限操作

SUPERADMIN 的内部工作入口是 Django Admin `/admin/`，而不是额外开发 Vue 超级管理后台。OPERATOR 负责日常运营工作台，但不自动获得 Admin、用户管理或负责人授权权限。

现实职位不自动映射：

```text
部长 != SUPERADMIN
会长 != SUPERADMIN
指导老师 != SUPERADMIN
```

# 权限模型

平台级角色：

```text
STUDENT
OPERATOR
SUPERADMIN
```

组织级身份：

```text
MEMBER
LEADER
```

展示职位：

```text
title
```

例如：

```text
organization = 科创与就业部
role = LEADER
title = 部长
```

权限判断必须包含资源范围。

正确：

```text
该用户是否是当前 organization 的 LEADER？
```

错误：

```text
该用户是不是某个组织的 LEADER？
```

后台权限永远由服务端验证。

前端隐藏按钮只负责用户体验，不构成安全授权。

# 校园动态

学生端保留既有 `/activities` 路径，但导航展示名为“校园动态”。它是公开活动与官方公告的共同浏览入口，不新增“公告”一级导航；两种内容仍是不同的业务对象、API 和数据表。

```text
Activity       要参加的事件：时间、地点、报名、容量
Announcement   要阅读的信息：学院 / 学校 / 平台公告、正文、外链、关联对象
Notification   与当前用户有关的个人消息：申请状态、活动变更、提醒
```

校园动态默认展示“全部”，按“近期活动”和“最新公告”两个有标题的区块呈现；不把报名事件与信息公告伪装成同一种卡片或按单一时间线混排。用户可切换：

```text
全部
活动
公告
```

`活动`与`公告`的筛选、搜索和分页状态由 URL 承载。首页仍保留“近期活动”和“通知公告”两个独立预览区块：前者的查看全部进入活动 tab，后者进入公告 tab。

## 公告

公告公开可见，来源必须标注为：

```text
学院公告
学校公告
平台公告
```

公告包含标题、发布日期、摘要、正文和可选站外原文链接；可关联一项竞赛、活动、组织或招新，也可完全不关联，用于学校、学院或平台的通用事项。

公告详情提供：

```text
来源标识
公告正文
查看原文（有学校官网等外链时）
查看关联对象（存在关联对象时）
```

平台只提供明确的站外跳转，不抓取、镜像或嵌入学校官网正文。普通公开公告默认不生成每位学生的未读消息；活动取消、临近提醒和申请结果等才以个人消息定向送达受影响用户。

# V0.1 统一业务决策

本节冻结此前容易被前端、后端或 coding agent 自行推断的业务细节。

详细字段、数据库约束和状态机以：

```text
docs/backend/database-design.md
```

为准。

## 未登录操作

公开信息保持可浏览。

当游客点击需要账号的操作：

```text
关注竞赛
发布组队
申请加入队伍
申请组织
报名活动
提交咨询
```

统一跳转：

```text
/login?next=<目标或返回路径>
```

登录成功后回到 `next` 继续原任务。

受保护操作不能只靠前端隐藏，后端仍需验证 Session 与权限。

---

## 正文格式

V0.1 需要运营编辑的长正文统一保存：

```text
Markdown
```

包括：

```text
竞赛介绍
准备建议
活动介绍
招新介绍
指南
FAQ 回答
通知
咨询与回复
```

数据库不以未经清洗的 HTML 作为正文事实来源。

---

## 重复操作

系统必须阻止：

```text
同一用户重复关注同一竞赛
同一用户重复占用同一活动名额
同一用户同时向同一招新提交多个有效申请
同一用户同时向同一组队发布多个有效申请
```

并发控制由数据库约束 + 后端事务完成，不能只禁用前端按钮。

---

## 招新通过后的组织身份

组织负责人接受 RecruitmentApplication 后：

```text
申请 -> ACCEPTED
+
创建 / 激活 OrganizationMembership
role = MEMBER
```

默认 `title` 可以使用申请岗位名称。

接受招新申请不会自动赋予：

```text
LEADER
```

---

## 组队关系

V0.1 不建立完整 TeamMembership 管理系统。

“我加入的队伍”由：

```text
TeamApplication.status = ACCEPTED
```

推导。

已有线下成员人数作为 `base_member_count` 保存，平台接受成员数实时统计，不额外维护一个容易漂移的 `current_count` 字段。

---

## 活动报名

一名用户对一场活动只有一条 Registration 记录。

取消后在报名窗口内重新报名：

```text
复用原记录
```

不创建重复报名行。

有容量限制的活动必须在数据库事务中检查名额。

---

## 内容状态

竞赛、活动、招新等正式内容把：

```text
发布生命周期
```

与：

```text
时间阶段
```

分开表达。

例如“报名中”“进行中”“已结束”优先由日期派生，避免后台状态因为无人手工切换而过期。

草稿、取消、归档等必须显式保存。

# 前端体验与可访问性约束

本节只规定产品级体验底线。具体颜色、Token、圆角、组件、动效、图标和暗色映射以 `FrontendDesign.md` 为唯一视觉事实来源。

## 语言

V0.1 产品界面只支持：

```text
简体中文（zh-CN）
```

要求：

- UI、通知、错误信息、帮助文本统一使用简体中文
- 日期、时间和数字按中文产品习惯展示
- 技术名词、竞赛专名和必要缩写可保留英文
- V0.1 不引入 i18n 框架，也不提供语言切换入口

---

## 外观模式

V0.1 前端支持：

```text
浅色
暗色
跟随系统
```

要求：

- 外观偏好是全局用户体验能力，不影响业务权限
- 未登录用户也可以使用主题切换
- 页面不得自行定义独立暗色主题
- 亮色与暗色都必须保持信息层级、状态含义和可读性一致

---

## 设计系统约束

正式产品 UI 必须遵循统一组件和图标体系：

```text
Nuxt UI v4
Tailwind CSS v4
Iconify
Lucide
```

产品 UI 不使用 emoji 作为导航、按钮、状态或功能图标。

常见 UI 图标不手写 SVG path，不使用 Unicode 箭头代替图标。

不引入第二套完整 UI 组件库。

---

## 可访问性

核心 UI 以 WCAG AA 为目标，亮色与暗色均需验证。

最低要求：

- 键盘可操作
- 焦点状态可见
- 图标按钮有可访问名称
- 表单有明确 Label 与错误提示
- 状态不只依赖颜色表达
- 支持 `prefers-reduced-motion`
- 浏览器 200% 缩放后核心流程仍可使用
- 移动端主要触控区域满足实际触控尺寸要求

---

## 响应式与任务效率

必须验证：

```text
Desktop
Tablet
Mobile
```

移动端不是桌面页面的机械缩小。

核心信息优先级：

```text
标题
状态
截止时间 / 活动时间
主要操作
关键元信息
辅助标签
装饰媒体
```

高频核心流程以进入相关页面后约 3 次有效交互内完成为设计目标，例如：

```text
活动详情 -> 报名 -> 确认
组队详情 -> 申请加入 -> 提交
招新详情 -> 申请加入 -> 提交
```
